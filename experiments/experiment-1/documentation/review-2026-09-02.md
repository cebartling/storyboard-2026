# Codebase review — 2026-09-02

A triage of an adversarial review of `experiment-1`, run at the point where the experiment is
being weighed for promotion. It is a snapshot, not a living document: the findings describe the
tree at commit `d0c77a0`, and the tiers below record what was decided about each, not what has
since been done. Work that lands should reference a finding id and then the id stops being
interesting.

## How the review was run

Three independent reviewers read the experiment in parallel, each confined to one dimension and
each starting with no knowledge of the others or of the code's history:

| Dimension               | Scope                                                                                                 |
| ----------------------- | ----------------------------------------------------------------------------------------------------- |
| Architecture and design | Layering, ports, ADR conformance, documentation drift, what collaboration/auth would cost to retrofit |
| Domain and persistence  | Aggregate invariants, fractional ranks, optimistic concurrency, schema, seed                          |
| Frontend                | Routes, Svelte 5 runes, the canvas, accessibility, component and e2e test quality                     |

They produced 33 findings; two pairs turned out to be the same defect seen from different sides,
leaving **32 distinct items**. All three were instructed to verify library behaviour against what
is actually installed rather than from memory, and to prefer a short high-confidence list over a
long speculative one.

### Provenance, and what it is worth

This matters more than the finding count, so it is stated plainly:

- **Reproduced.** Three findings were demonstrated by running code — F1 and D1 by writing a
  throwaway test that failed, D2 by executing the DELETE statements against the committed
  migrations. These are facts about the tree.
- **Read.** The rest are judgments from reading the code. They are specific and cite file:line,
  but they have not been independently re-verified, and a reviewer's confident tone is not
  evidence. Treat each as a hypothesis with a known place to check it.

Nothing in this document should be actioned without first confirming it still holds — several
findings are about code that changes often.

## Verdict

The parts of the design that were most in question came back sound. The domain really is pure: it
imports nothing but `fractional-indexing`, the repository leaks no Drizzle types, and routes never
reach past the use cases. Optimistic concurrency is airtight for the current single-process SQLite
deployment — the versioned `UPDATE` is the first statement in the transaction, and a failed child
insert was confirmed to roll the whole thing back. The client genuinely cannot influence ranks.
`camera-storage.ts` survives hostile input. Svelte 5 runes usage is idiomatic throughout.

Two things are broken today, and one architectural question the experiment was built to answer has
not actually been answered.

The recurring theme, and the most useful single output of the review: **both proven bugs live
exactly where the tests are absent or tautological.** Deletes are never exercised end to end;
`moveStory` is never driven with stale neighbours. The test suite's shape predicted where the
defects would be.

## Tier 1 — Broken now, fix before anything else

### F1 · Every delete of an activity or step throws a `TypeError`

`src/routes/maps/[mapId]/+page.svelte:136` · **reproduced**

Svelte 5.57's `bind:this` writes `null` into the array slot on teardown
(`internal/client/dom/elements/bindings/this.js:71`), but `trackMaxHeight` filters only
`el !== undefined`. Keyed-each removals leave trailing `null`s that never clear, so the next rerun
calls `observer.observe(null)` and reads `.offsetHeight` off it. With no `<svelte:boundary>`,
Svelte rethrows out of the flush. The declared type is `(HTMLDivElement | undefined)[]`, so
`svelte-check` cannot catch it.

Every `deleteActivity` / `deleteStep` round-trips through `invalidateAll()` and hits this path.

Fix: filter with `el != null` and widen the type to include `null`. The real fix is F7 — a delete
that is never tested is a delete that breaks.

### D1 · `moveStory` can produce duplicate ranks, surfacing as a 500 instead of a 409

`src/lib/domain/story-map.ts:140` · **reproduced**

`resolveRank` verifies that `beforeId`/`afterId` are members of the target scope but never that
they are _adjacent_, nor that a `null` side is genuinely the end. Because
`generateKeyBetween(prev, null)` and `generateKeyBetween('a0', 'a2')` both return `prev`'s integer
part incremented, and `addStory` appends with exactly those consecutive keys, a stale drop collides
**deterministically rather than by luck**.

The domain returns the invalid aggregate without throwing — `domain-model.md:52` claims it enforces
per-scope rank uniqueness, and it does not. The partial unique index rejects the save, and
`run-action.ts:36` treats the resulting `SqliteError` as an unexpected fault and returns a generic 500. This is precisely the lost-update situation the 409 path exists to report. When the derived
key happens not to collide, the card silently lands somewhere the user did not choose.

Reproduction: scope `[A='a0', B='a1']`; `moveStory(X, step, null, beforeId=A, afterId=null)` yields
`X.rank === 'a1' === B.rank`; `save()` then throws `UNIQUE constraint failed: stories.step_id,
stories.rank`, correctly rolled back.

Fix: assert adjacency in `resolveRank` and throw `ConflictError` (not `InvariantError`) on
violation — a stale caller view is exactly what 409 means, and `run-action.ts` already maps it.

### F2 · Clicking the dialog's own padding closes it and discards typed input

`src/lib/components/modal.svelte:74` · read

The backdrop-close branch treats `e.target === dialogEl` as "outside the content", and its comment
claims all content lives in a child wrapper. It does not: the `<dialog>` itself carries `p-5`, and
the close button, `<h2>`, and body wrapper are direct children — so the 20px padding ring and the
16px gap under the title are the dialog's own hit area. A press there runs `onClose` with no
confirmation, losing whatever was typed.

Grouped into Tier 1 because it is silent data loss on an everyday interaction, not because it
crashes.

Fix: move the padding to an inner wrapper, or compare the point against
`dialogEl.getBoundingClientRect()`.

## Tier 2 — Decide before committing to this architecture

These are not bugs. They are the questions the experiment exists to answer, and the review's view
is that one of them has been quietly left open.

### A1 · Concurrent edits to _different_ cards are mutually exclusive

`src/lib/server/repository/drizzle-story-map-repository.ts:110` · read · **highest retrofit cost**

`save()` bumps a single `maps.version` and deletes and reinserts every child row. Two people
editing unrelated cards therefore conflict: the second writer gets a 409. Worse for the retrofit,
every domain function returns a whole new `StoryMap` with no delta, command, or event — so there is
nothing to broadcast, diff, or merge.

ADR 0004 defers the question as _"is whole-map save fast enough?"_ — a throughput question. The
expensive one is contention. Adding collaboration later would mean reshaping the domain's return
types, the repository port, and the client's `invalidateAll()` sync loop simultaneously.

The decision to make now is not "build collaboration". It is: run the two-browser experiment, write
down what happens, and either amend ADR 0004 to state that the aggregate boundary must move before
collaboration is possible, or start returning `{ map, change }` from domain mutations so a
per-operation layer can be added later without rewriting the core.

### A2 · Three of four rank scopes are unexercised, and the docs describe a feature that does not exist

`src/lib/domain/story-map.ts:373` · read

`moveStory` is the only rank-_between_ path in the codebase. Activities, steps, and slices can only
be appended via `rankAtEnd`. Meanwhile `domain-model.md:60` states an invariant for moving a Step
to a different Activity, and `glossary.md:39` describes dragging left/right to reorder the
backbone. Neither exists in the domain, use cases, routes, or e2e.

Backbone reordering is the core story-mapping interaction after story priority, and it is the one
that would actually stress the `(activityId)` and `(mapId)` rank scopes. A vertical slice that
skips it has not tested the ranking design.

Decide: either add `moveStep` / `moveActivity` / `moveSlice` to the domain with tests, or strike
the claims from the docs and record the gap as deliberate scope.

### A3 · ADR 0005 and ADR 0004 claim opposite things

`documentation/adr/0005-fractional-ranks.md:83` · read

ADR 0005's consequences call single-row writes for drags "the payoff this decision exists for". ADR
0004's whole-map save rewrites every child row on every mutation, so a drag is an N-row write
regardless of rank scheme. The fractional-rank benefit is real _in the domain_ — no sibling
renumbering — but is unrealised at the write path.

Resolution follows A1: whichever way that decision goes, both ADRs need to agree.

### A4 · The `AiAssistant` port has no consumer, and ADR 0007 says otherwise

`src/lib/domain/ports.ts:32` · read

Nothing references `aiAssistant` or `suggestStoriesForStep` outside `deps.ts:26`, which constructs
`NullAiAssistant`. ADR 0007:38 states the null implementation lets "the rest of the app (use cases,
routes) be wired against the port today"; nothing is. The "contract style is the commitment" claim
is a doc comment with no consumer, type, or test enforcing it — so it does not actually constrain
the first real AI feature, which is the entire justification for the port existing pre-emptively.

Decide: delete the port and keep ADR 0007 as recorded intent, or add one consuming use case with a
fake assistant so the seam is demonstrated rather than asserted. Leaving it as-is is the only
option with no defence.

### A10 · Authentication is a port-signature change, not middleware

`src/lib/domain/ports.ts:20` · read

`listSummaries()` takes no scope and returns every map, `load(id)` has no caller identity,
`App.Locals` is empty, and the schema has no owner column. Excluding auth is deliberate and fine —
but nothing records that adding it later changes the repository port's signature and every action,
rather than slotting in as a layer. One line in ADR 0006 or `architecture.md` prevents a wrong
assumption.

## Tier 5 — Test debt

Listed together because they are one problem, not eight. The suite is genuinely strong on failure
paths — the e2e uses `page.route` to force a late-failure race, and `camera-math.ts` has real edge
cases — but it has a consistent blind spot: **it tests that things are wired, not that they work.**

| id  | file:line                                  | Gap                                                                                                                                                                                                                                                            |
| --- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F7  | `board-dialogs.svelte.spec.ts:55`          | No delete flow is exercised anywhere. The specs assert the right hidden id is present and deliberately never submit; neither e2e file clicks a Delete button. This is why F1 was invisible.                                                                    |
| D3  | `story-map.test.ts:327`                    | The test named for invariant enforcement only ever calls `addStory`. Append always produces a fresh key, so rank uniqueness is trivially true regardless of what `moveStory` does — it passed while D1 was reproducible.                                       |

The delete test checks only that activities are gone, not stories or slices.                                     |
| D8  | `rank.test.ts:6`                           | `rankBetween(null, null)` and `rankAtEnd([])` are asserted only to be _strings_; any non-throwing implementation passes.                                                                                                                                       |
| F9  | `modal.svelte.spec.ts:143`                 | `dialog.dispatchEvent(new MouseEvent('mousedown'))` makes `e.target === dialogEl` true by construction, so it validates the branch but not the layout claim underneath it — which is false (F2).                                                               |
| F11 | `+page.svelte:85`                          | The restore-vs-fit branch and the `hydratedMapId` gate have no e2e coverage; a regression that saved before hydrating would pass.                                                                                                                              |

> A pattern worth naming, because it recurred in this session's own work: several component tests
> dispatch synthetic events directly at elements, which bypasses hit-testing entirely. That is a
> reasonable trade for testing handler logic, but it means those tests can never catch a z-order,
> overlay, or `pointer-events` regression — and F2 and F5 are both exactly that kind of regression.
> Where a test's whole point is geometric, it needs a coordinate-driven click or a
> geometry assertion, and it needs to be checked by mutation: an assertion that passes against a
> deliberately broken implementation is not an assertion.

## Suggested order

1. **F1, D1, F2** — with the tests that should have caught them (F7, D3, F6), written first and
   checked by mutation.
2. **A1** — run the two-browser experiment and write down the answer. It gates A3, and it is the
   finding most likely to change what this experiment concludes.
3. **A2 and A4** — decide, then make code and docs agree either way.
4. Tier 3, then Tier 4 as a single documentation pass.

Tier 5 is not a phase. Each item belongs to whichever change above touches its code.
